# Как ставить задачу агенту

Основа: официальные рекомендации
[Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
и результаты работ из [4_studies](../4_studies/README.md). Примеры из
Claude Code, но принципы не зависят от клиента.

## 1. Напишите то, чего агент не видит

Агент сам читает код, структуру, тесты и соглашения. Нужно сообщить то,
чего в репозитории нет: решение команды, нужную переменную окружения,
вашу оценку «что считать готовым», выбор между двумя разумными
подходами. Проверка перед тем как писать: найдёт ли агент это в коде и
пойдёт ли искать. Если оба ответа «да», не пишите.

| Вместо | Лучше |
| --- | --- |
| «исправь баг входа» | «пользователи не входят после тайм-аута сессии; смотри обновление токена в src/auth/, напиши падающий тест, затем исправь» |
| «добавь виджет календаря» | «по образцу HotDogWidget.php сделай виджет календаря с выбором месяца и листанием лет, без новых библиотек» |

Передавайте готовое, а не пересказ: файл через `@путь`, скриншот,
вывод команды. Если нужна полная версия с краевыми случаями, скажите
об этом прямо: агент по умолчанию делает минимальное. Фразы вроде
«думай шаг за шагом» это обычный текст, глубину рассуждения задаёт
уровень effort. Для исследования достаточно и расплывчатого запроса.

## 2. Если требования не ясны, пусть агент спросит

Попросите агента опросить вас и записать спецификацию в файл
(например `SPEC.md`), затем начните новую сессию для реализации: с
чистым контекстом и письменным определением готовности. Тот же файл
пригодится ревьюеру.

## 3. Дайте проверку, которая возвращает «да» или «нет»

Без проверки агент останавливается, когда работа «выглядит готовой».
Проверкой может быть тест, код выхода сборки, линтер, сравнение вывода с
эталоном, скриншот рядом с макетом. Самая полезная строка в файле
инструкций это команда запуска такой проверки. Просите доказательство
(команду и вывод), а не «всё проходит».

Строгость нарастает: просьба в промпте; условие готовности, которое
проверяет отдельная модель; Stop hook, который не даёт завершить ход,
пока проверка не пройдена ([hooks](../1_setup/5_hooks.md)); ревью
другим исполнителем, не видевшим ход работы.

Исследования подтверждают, что полагаться на самопроверку нельзя:
терминальные агенты находят около 61% своих неверных решений
([проверка результата](../4_studies/7_verification.md)), а прохождение
существующих тестов не доказывает верность патча
([бенчмарки](../4_studies/2_benchmarks.md)). При ревью по
спецификации добавляйте «пропусти стиль»: ревьюер, которого просят
искать проблемы, найдёт их всегда.

## 4. Что класть в файл инструкций

Только то, чего нет в коде: команды проверки, места, где код вводит в
заблуждение, решения вне репозитория, то, что пришлось исправлять
дважды. Короткий файл (около 200 строк и меньше) работает лучше длинного.
Если агент игнорирует строку, а ЗАГЛАВНЫЕ БУКВЫ не помогают, строка
либо потерялась в длинном файле, либо это правило без исключений и ему
нужен hook. В эксперименте Evaluating AGENTS.md файлы, созданные LLM,
не улучшили результат и повысили стоимость примерно на 20%; обзоры
репозитория не помогли
([контекст и инструкции](../4_studies/3_context_instructions.md)).
Подробно: [инструкции](../1_setup/1_instructions.md).

## 5. Когда делегировать субагентам

Субагенты окупаются, когда нужны:

- независимые части работы одновременно;
- вынос длинного вывода (полный прогон тестов, широкий поиск) из
  основного разговора;
- ревьюер, не видевший, как писался код;
- набор инструментов уже, чем у основной сессии (ревьюер без права
  правки).

Цена: токены (у каждого свои запросы), иногда и время, так как новому
субагенту нужно собрать контекст заново. Модель по умолчанию та же, то
есть вы получаете параллелизм или свежий взгляд, но не более умный ответ.
Что снижает расход: недорогая модель для простых задач, короткие
сводки в ответе, ограниченный набор инструментов, контроль расхода по
типам субагентов.

Что говорят исследования: на связанных задачах кодинга мультиагентные
схемы чаще вредят, чем помогают, а токенов тратят в разы больше
([Scaling Agent Systems](../4_studies/4_multi_agent.md)); если
командой пользуетесь, выгоднее вкладывать деньги в планирование, а не в
исполнителей. Как настроить: [субагенты](../1_setup/3_subagents_roles.md).

## 6. Параллельная работа

Каждой параллельной сессии нужен свой checkout, чтобы правки не
пересекались (в Claude Code это worktree). Вторая сессия самый простой
независимый ревьюер: пусть она проверит код, не наблюдавший его
написания, и перенесите замечания в первую.

## 7. Управление сессией

- Следите за первой минутой и останавливайте агента, как только он
  уходит не туда.
- После двух неудачных исправлений начните с чистого контекста с одним
  улучшенным промптом: третье исправление добавляется к разговору, где
  уже две неудачи.
- Откат кода и разговора к прежней точке делает рискованные подходы
  дешёвыми.
- Между несвязанными задачами очищайте контекст, при долгой работе
  сжимайте с указанием, что сохранить.
- Для многодневной работы называйте сессию, чтобы возобновить её
  позже.

## 8. Расход и контекст

Каждый запрос отправляет весь разговор, поэтому лишний контекст стоит
денег. Смотрите разбивку расхода по навыкам, субагентам, плагинам и MCP.
Кэш промпта живёт около часа на подписке и пять минут на ключе API или
при оплате кредитами. Простое маскирование старого вывода инструментов в
эксперименте JetBrains снижало стоимость примерно вдвое без потери
качества ([токены и стоимость](../4_studies/8_tokens_cost.md)).
Подробно: [память и контекст](../1_setup/8_memory_context.md).

## 9. Передача состояния между сессиями и агентами

Файл памяти одного клиента не становится памятью другого. При паузе или
смене клиента записывайте: цель и стадию, подтверждённые факты с
источниками, принятые решения, изменённые файлы, пройденные проверки,
оставшиеся риски, следующий шаг и условие остановки. Секреты не
включайте. Это практическая рекомендация; для долгих задач она
согласуется с инженерным разбором Anthropic о харнессах длинных
агентов ([reviews](../4_studies/reviews/context-and-evals.md)).
